### 协作单 39.0：选股「数据服务未就绪：HTTP 503」治本修复（P1）
- **根因**：① 快照刷新期间 `_ready=False` 致整个服务短暂不可用（旧缓存也下线）；② 刷新由每个请求触发，高峰期反复重建（全市场 300 天 OHLCV 约 121MB）；③ `get_all_snapshot` 每次全表遍历再按 codes 过滤（无索引）。
- **修复（`backend/core/service/snapshot_service.py` 3 点落地）**：
  1. **双缓存热切换**：`_refresh_if_needed` 触发刷新时不再置 `_ready=False`，刷新期间旧缓存持续服务；`_reload_async` 新数据就绪后原子替换缓存。
  2. **独立定时刷新**：新增 `_periodic_refresh_loop` 后台线程（周期 `CACHE_CHECK_INTERVAL`=600s）唯一触发刷新；`get_all_snapshot` / `get_incremental_snapshot` / `latest_trade_date` / `get_history_snapshots` 四请求路径移除 `_refresh_if_needed()`，只读缓存。
  3. **按 codes 索引**：传 codes 时改用 `snapshot_cache.get(code)` 直查（O(K)），未传才全量遍历（O(N)）。
- **新增单测**：`backend/tests/test_snapshot_refresh.py` 10 用例（热切换保持 ready / 请求不触发刷新 / codes 索引 / ETL 窗口避让），全部通过。
- **验证**：`test_snapshot_history.py` 14 例回归全过；服务重启（launchd kickstart，清理占用 8000 的旧实例）日志确认定时线程启动；API 实测 `/api/snapshot/ready` 200（ready=true，latest=2026-09-18，7869 只）、`/api/snapshot/all?codes=000001` 200（0.006s）、`/incremental` 200。
- **结果**：方舟 21:35 复核通过，协作单 39.0 → CLOSED。
