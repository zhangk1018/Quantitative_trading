### 1. 美股日线清洗僵死事故：排查与处置（P0）

**触发**：K 反馈系统监控看板「美股数据监控」的日线清洗显示 **○ 待执行** 告警。

**查证结论：告警属实，且看板判定准确**。完整根因链（三条缺一不成立，均有原始证据）：

1. **08:30 计划触发时机器处于睡眠**——`pmset -g log` 显示 07:59:40 进入 Sleep、09:59:41 才 DarkWake，launchd 错过触发点，在唤醒瞬间补跑（`us_job.stdout.log` 启动时间 09:59:41 与 DarkWake 精确吻合）。故 8:30~9:59 区间看板查不到美股当日记录，回退数据表评估得「最新 9/29 < 期望 9/30」→ 返回 pending → 前端渲染 amber「○ 待执行」，**该告警是正确示警**；
2. **补跑后进程被反复冻结**——10:00:26 起系统进入 Maintenance Sleep 循环，每次 DarkWake 仅 40~50 秒即回睡；
3. **半死 socket 永久阻塞**——10:50:21 入睡瞬间，进行中的 `ak.stock_us_daily`（新浪）HTTPS 请求被冻结；唤醒后 TCP 连接半死，而 **AkShare 各接口不暴露 timeout 参数（requests 默认无限等待）→ 永久阻塞在 `SSL_read`**。证据：`sample <pid> 1` 抓栈显示主线程 100% 阻塞于 `SSL_read`→`read`；`lsof` 显示到新浪 CDN 的 socket 仍 ESTABLISHED；进程 CPU 时间 `0:00.00`、日志零输出。

**影响面**：美股 9/30 日线 205 只仅落 61 只（29.8%），其后指标/形态/信号/宽表/Parquet 全链停摆，`task_run_log` 长期停在 `running`。

**处置**：
- 终止僵死进程（PID 91954/91973），确认无残留；
- 将 `task_run_log` 中被中断的 `us:日线清洗` running 记录**显式标记为 failed** 并注明原因（保留审计痕迹，不掩盖异常）；
- 以 `caffeinate -i -s` 包裹重跑 `us_job_runner`（防再次被睡眠冻结），日线从断点续跑——校验 `etl_control` 游标 `last_processed_code='DTE'`（窗口 `2026-09-30~2026-09-30`）与库中已落 61 只的末位代码**严格一致**，故断点复用安全；
- **数据已补齐**：美股 9/30 `stock_quotes 205` / `stock_indicators 202` / `stock_daily_snapshot 204` / `trade_signals 182` / `latest_quotes_us.parquet 204 行 × 93 列`（日期 20260930）。

### 2. 修复 A：下载层网络硬超时（P0，治本）

`backend/collector/datasource/akshare.py` 新增 `network_deadline(seconds)` 上下文管理器 + `NetworkTimeoutError`：
- 以 `SIGALRM`/`setitimer` 给每次 AkShare 调用设硬超时；**仅主线程生效**（ETL 各脚本均为串行单线程调用），非主线程退化为不设限；
- 阈值：单标的日线/交易日历/列表 `AKSHARE_NETWORK_TIMEOUT=60` 秒，全市场快照（`stock_hk_spot` 一次返回全市场）`AKSHARE_BULK_NETWORK_TIMEOUT=180` 秒，均可环境变量覆盖；
- 包裹点：`_fetch_hk`/`_fetch_us`（两次调用分别计时）、`_trade_dates_from`（每个 getter 分别计时，超时后降级下一数据源）、`_fetch_hk_list`/`download_hk_snapshot_all`；
- 超时异常由调用方原有 `try/except` 兜底（跳过该标的或降级），不再拖死进程；顺带为 `download_single` 等原先**静默 `return None`** 的 except 补 `WARNING` 日志（异常显式化）；
- 实测正常下载未受影响（AAPL 10043 行 / 5.6s）。

### 3. 修复 C：launchd caffeinate 防睡眠 + pmset 定时唤醒（P0，运维层）

- 9 个**定时**任务 plist（`daily_job_runner.stage1/2/3`、`hk_job`、`us_job`、`bar_aggregation.weekly/monthly`、`hk/us_basic_sync.saturday`）的 `ProgramArguments` 前置 `/usr/bin/caffeinate -i -s --`，任务运行期间阻止系统休眠。**不含** `postgresql`/`backend` 两个常驻服务（否则机器永不睡眠）；
- 已复制到 `~/Library/LaunchAgents/` 并**逐个** `unload && load -w`（未动 postgresql/backend，避免数据库与 API 中断）；`launchctl print` 确认 argv 已含 caffeinate；
- **验证 caffeinate 不削弱错误检测**：实测其如实转发退出码与输出流（`exit 3`→3、`exit 7`+双流→7 且 stdout/stderr 正确分流），故 runner 的 `TASK_RESULT` 解析与失败重试逻辑不受影响；
- `sudo pmset repeat wakeorpoweron TWRFS 08:25:00` 已由 K 执行成功（`pmset -g sched` 显示 `wakepoweron at 8:25AM Some days`，即周二~周六，对应美股 08:30 任务），解决「触发时机器睡着 → launchd 直接错过」这一环。

### 4. 修复 D：Parquet 导出失败不再静默（P1）

`backend/clean/enrich/export_parquet.py`：原实现四个失败分支（连接失败/宽表为空/当日无数据/导出异常）只打印 `TASK_RESULT{error}` 便 `return`，**进程退出码仍为 0** → runner 记为成功、既不重试也不告警。现改为函数返回 `bool`，`__main__` 用 `sys.exit(0 if ok else 1)` 上报。

**顺带澄清一个假象**：本次事故中那次 Parquet 失败（`OSError [Errno 18] Cross-device link`）实为**本地 Trae sandbox 拦截备份轮转的 rename/unlink** 所致（报错原文含 `TRAE Sandbox Error: hit restricted`），**生产 launchd 环境无此问题**——非 sandbox 下重跑退出码 0、备份轮转正常（bak1←14:12 版，bak3←9/30 版）。已在文档中明确区分，避免后人误判。
