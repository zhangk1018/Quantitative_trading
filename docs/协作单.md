## [43.0-SNAPSHOT-MARKET-DATE-20260929] 快照缓存按单一全局最新交易日加载 → 最新快照日滞后的市场整市缺失，自编指标选股恒 0 只（P0）

| 字段 | 内容 |
|------|------|
| **状态** | CLOSED |
| **提单方** | 方舟 |
| **接单方** | 量量（后端） |
| **日期** | 2026-09-29 |
| **影响范围** | backend（`snapshot_service.py`）；前端 `/api/snapshot/all` 的全部消费方（自编指标选股；回测范围模式不受影响） |
| **优先级** | P0 |

**定位路径**:
- `backend/core/service/snapshot_service.py` `_query_meta` L184-188：`SELECT MAX(trade_date) FROM stock_daily_snapshot` —— **全表单一全局最新交易日，无市场维度**
- 同文件 `_load_from_db` L383-394：`SELECT ... FROM stock_daily_snapshot WHERE trade_date = %s`（= 上述全局 latest）→ 只有该日期的行进入 `_snapshot_cache`
- 同文件 `_load_from_db` L198-202（`_query_meta` 内的快照维度计数）与 `_save_cache`：`row_hash` 的快照维度同样是「该单一日期行数」，因此**缓存命中判据也无法暴露缺失市场**
- 对照：OHLCV 维度用的是 `trade_date <= latest`（L340-350），不丢滞后市场；**仅快照维度用了等值日期**

**问题描述**:
快照缓存加载只保留「全局最新交易日」的快照行，导致**任何最新快照日晚于/早于全局 latest 的市场被整市剔除**，`/api/snapshot/all` 对该市场返回 `total=0`。前端自编指标选股是唯一依赖 `/api/snapshot/all` 的路径（技术指标/基本面筛选走 parquet `/api/stocks/`，不受影响），因此现象为：**同一市场里技术指标能筛出股票，自编指标却恒 0 只，且无任何报错**。

实测证据（2026-09-29 09:00 前后，后端进程自 09-28 21:23 起未重启）：

1. DB 各市场最新快照日不齐：`cn` 2026-09-28（5210 行）、`hk` 2026-09-28（2169 行）、`us` **2026-09-25（205 行）** → 全局 `MAX(trade_date)` = 2026-09-28
2. 磁盘缓存 `data/cache/snapshot.pkl` = **7379 条 = cn 5210 + hk 2169，无任何美股**（与「只加载 9/28 行」完全吻合）
3. live 接口（`zhangk` 会话）：
   - `GET /api/snapshot/all?codes=600519,000001` → `total=2`，ohlcv 各 201 根 ✅
   - `GET /api/snapshot/all?codes=00700.HK,0001.HK&market=hk` → `total=1`（0001.HK 200 根）
   - `GET /api/snapshot/all?codes=AAPL,MU,TSLA&market=us` → **`total=0`** ❌ → 美股自编指标选股恒 0 只（当前可复现）
4. 历史同类事故（即 K 本次反馈的沪深 0 只）：2026-09-25 为 A股中秋休市（`stock_quotes` 无 cn 9/25 行）、港美股照常开市 → 全局 latest 落在 9/25 的 hk/us，cn 最新为 9/24 → **沪深被整市剔除**。后端日志佐证：
   - `2026-09-26T20:51:35` / `2026-09-28T09:32:43` / `2026-09-28T15:15:06` 三次启动均 `✅ 缓存加载完成：205 条快照`（205 = 当日美股行数，即缓存只剩美股）
   - 9/28 全天 `全量快照请求：0只股票` 共 **326 次**（`/api/snapshot/all` 全部返回空）
   - 9/28 21:23 缓存被判定失效重建后才恢复（`📋 快照加载完成：5210 只股票`）

> 结论：这不是 41.0 的复发（41.0 修的是 `row_hash` 不含快照维度），而是**快照维度的日期口径本身缺市场维度**——只要某市场最新快照日与全局 latest 不一致（美股因 `us_job_runner` 次日 08:30 跑、天然滞后一个交易日；A股遇节假日休市、也会滞后），该市场就会静默整市消失。

**预期修复（量量后端）**:

   `SELECT ... FROM stock_daily_snapshot s JOIN (SELECT market, MAX(trade_date) d FROM stock_daily_snapshot GROUP BY market) m ON s.market=m.market AND s.trade_date=m.d`（或等价 CTE / `DISTINCT ON (code) ... ORDER BY code, trade_date DESC` 取每只股票最新一行），保证每个市场都进缓存。

## [44.0-SNAPSHOT-OHLCV-WINDOW-20261010] `/api/snapshot/all` OHLCV 历史窗口固定 300 自然日（≈196~205 根）→ ≥200 周期自编指标在部分市场永不生效，同一指标跨市场行为不一致（P1）

| 字段 | 内容 |
|------|------|
| **状态** | CLOSED |
| **提单方** | 方舟 |
| **接单方** | 量量（后端） |
| **日期** | 2026-10-10 |
| **影响范围** | backend（`snapshot_service.py`）；前端自编指标选股（`/api/snapshot/all` 唯一消费方）跨市场一致性与长周期指标可用性 |
| **优先级** | P1 |

**定位路径**:
- `backend/core/service/snapshot_service.py` **L48**：`HISTORY_DAYS = 300`（自然日）
- 同文件 **L396-405**（OHLCV 缓存构建/刷新）：
  `SELECT … FROM stock_quotes WHERE cycle='1d' AND trade_date >= CAST(%s AS DATE) - CAST(%s AS INTERVAL) AND trade_date <= %s ORDER BY code, trade_date`，参数 `(self._latest_trade_date, f'{HISTORY_DAYS} days', self._latest_trade_date)` —— 窗口用**全局** `latest` 倒推 300 自然日
- 消费方：`GET /api/snapshot/all`（前端自编指标选股的 K 线唯一来源）

**问题描述**:
300 自然日 ≈ 196~205 个交易日，且**各市场在同一自然日窗口内包含的交易日数不同**（节假日/休市差异 + 全局 latest 倒推）。实测（2026-10-10，登录会话直连）：

| 市场 | 样本 | `stocks[].ohlcv.length` |
|---|---|---|
| cn | `600519` | **196** |
| hk | `0813.HK` | **201** |
| us | `CMG` | **205** |

后果：
1. **≥200 周期的指标在部分市场永不生效**：形如 `ema(close, 200)` 且带 `if n >= 200:` 守卫的公式，在 cn（n=196）**永远进不去该分支**，而 us（205）/hk（201）能进 → **同一自编指标在沪深/港股/美股得到不同的满分上限与命中数**，跨市场结果不可比、也不可解释。
2. 长周期指标（MA200/EMA200/年线）在当前窗口下几乎不可用（沪深直接失效）。
3. 上述差异在选股页表现为「同一指标在某市场命中明显偏多/偏少、像是没起作用」，会把排查引向指标/前端，而真实原因是后端 K 线窗口不足。
4. 该窗口与 43.0 无关（43.0 修的是「快照维度」缺市场日期；本次是「OHLCV 维度」的窗口长度/口径）。

**预期修复（量量）**:
1. OHLCV 历史窗口改为能**稳定覆盖 ≥ 250 个交易日**（建议 `HISTORY_DAYS ≥ 450` 自然日以留足节假日余量），或改为**按交易日条数**截取（如每只股票保留最近 N=250~300 根），彻底摆脱自然日→交易日的换算不确定性。
2. 窗口基准改为**各市场自己的 latest**（复用 43.0 已落地的 `_market_latest`），避免滞后市场窗口更短。
3. 若担心缓存体积/加载耗时，可分市场设置窗口，或对长周期指标需求单独放宽；请给出改前/改后的**缓存文件体积**与**加载耗时**对比。

## 工作流

### 状态机

```
NEW（方舟/量量提单）
  │
  ▼
ASSIGNED（量量/方舟 认领并开始处理）
  │
  ▼
VERIFY（处理完成，待对方验证）
  │
  ├─ ✅ → CLOSED（验证通过，关闭）
  │
  └─ ❌ → REOPENED（验证不通过 → 回到 ASSIGNED）
```

### 各角色职责

| 角色     | 在工单中的职责                                                 |
| ------ | ------------------------------------------------------- |
| **方舟** | 发现前端/后端问题 → 提单（NEW）；量量修复后做前端侧验证（VERIFY→CLOSED/REOPENED） |
| **量量** | 修复后端/数据问题（ASSIGNED→VERIFY）；方舟提的后端问题，量量认领修复              |
| **K**  | 仲裁争议（REOPENED 后双方无法达成一致时）；最终验收                          |

### 生命周期规则

1. **提单方**（通常是发现方）写入工单时状态为 `NEW`
2. **处理方**认领后改为 `ASSIGNED`，开始修复
3. **处理方**完成修复并验证后改为 `VERIFY`，**同时**在 topics.md 追加一行通知对方
4. **验证方**从前端/使用侧验证后：

   - 验证通过 → `CLOSED`

   - 验证不通过 → `REOPENED`，注明原因，**同时**在 topics.md 追加一行通知处理方
5. 一个工单最多 REOPENED 2 次，第 3 次需要 K 介入仲裁
