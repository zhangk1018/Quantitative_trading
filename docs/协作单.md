# 协作单

> 方舟与量量之间的工单系统，基于增强黑板模式。
> 最后更新：2026-09-19
> 注：已 CLOSED 的工单移入 `docs/协作单_归档.md` 存档，不在本文件维护；本文件仅保留 NEW/ASSIGNED/VERIFY（进行中或待验证）的工单。

***

## 工作流

### 状态机

```
NEW（方舟/量量提单）
  │
  ▼
ASSIGNED（量量/方舟 认领并开始处理）
  │
  ▼
VERIFY（处理完成，待对方验证）
  │
  ├─ ✅ → CLOSED（验证通过，关闭）
  │
  └─ ❌ → REOPENED（验证不通过 → 回到 ASSIGNED）
```

### 各角色职责

| 角色     | 在工单中的职责                                                 |
| ------ | ------------------------------------------------------- |
| **方舟** | 发现前端/后端问题 → 提单（NEW）；量量修复后做前端侧验证（VERIFY→CLOSED/REOPENED） |
| **量量** | 修复后端/数据问题（ASSIGNED→VERIFY）；方舟提的后端问题，量量认领修复              |
| **K**  | 仲裁争议（REOPENED 后双方无法达成一致时）；最终验收                          |

### 生命周期规则

1. **提单方**（通常是发现方）写入工单时状态为 `NEW`
2. **处理方**认领后改为 `ASSIGNED`，开始修复
3. **处理方**完成修复并验证后改为 `VERIFY`，**同时**在 topics.md 追加一行通知对方
4. **验证方**从前端/使用侧验证后：

   - 验证通过 → `CLOSED`

   - 验证不通过 → `REOPENED`，注明原因，**同时**在 topics.md 追加一行通知处理方
5. 一个工单最多 REOPENED 2 次，第 3 次需要 K 介入仲裁

## [39.0-SNAPSHOT-503-20260918] 选股报「数据服务未就绪：HTTP 503（等待超过 120s）」——快照服务全量刷新期对外不可用

| 字段 | 内容 |
|------|------|
| **状态** | **CLOSED（方舟复核通过）** |
| **提单方** | 方舟 |
| **接单方** | 量量（后端） |
| **日期** | 2026-09-18 |
| **影响范围** | backend（snapshot_service）+ frontend（选股时 OHLCV 拉取等待） |
| **优先级** | P1 |

**定位路径**:
- 前端：`frontend/src/features/stock-picker/services/CustomIndicatorService.ts` `fetchOhlcvBatch`（`GET /api/snapshot/all`）在 503 时调 `waitReady` 轮询 `/api/snapshot/ready`，超时 `OHLCV_READY_WAIT_MS=120s` 报错。
- 后端：`backend/core/service/snapshot_service.py`
  - `get_all_snapshot` 每次调用 `_refresh_if_needed()`（L697）+ `_ensure_ready()`（L698）+ `_ensure_ohlcv_loaded()`（L700）
  - `_refresh_if_needed`（L476）检测到数据变更（每天新交易日或 row_hash 变）→ 置 `_ready=False` + 异步 `_reload_async`（L523）全量重建
  - `_reload_async` 加载全市场 OHLCV（全市场 × 300 天，约 **121MB** pickle）+ 快照，完成后才 `_ready=True`
  - `get_all_snapshot` L702-724 每次遍历**全部** snapshot_cache + ohlcv_cache 再按 codes 过滤（无索引）

**问题描述**:
选股偶尔报「OHLCV 数据拉取失败，已重试 2 次: 数据服务未就绪：HTTP 503（等待超过 120s）」。根因链：
1. 每次 `/api/snapshot/all` 都触发 `_refresh_if_needed()`；检测到数据变化（每日新收盘即触发）就**立即 `_ready=False`** 并异步全量重建。
2. 全量重建（全市场 300 天 OHLCV 121MB）耗时可能 >120s；期间所有快照请求返回 503。
3. 前端 `waitReady` 等 120s 超时报错。
**关键矛盾**：异步刷新期间**整个快照服务对外不可用**（`_ready=False` 让旧缓存也下线了），且**刷新由每个请求触发**、高峰期不可控，前端只能被动等待/超时。

**预期修复（量量后端，3 点）**:
1. **双缓存热切换，刷新期不中断服务**（最关键）：`_reload_async` 已在用临时缓存 + 原子替换（L523-574 双缓存设计已有雏形），建议**刷新中保持 `_ready=True` 继续用旧缓存服务**，仅在新数据就绪后原子替换 `_ohlcv_cache/_snapshot_cache`。用户刷新期选股零中断，不再 503。
2. **独立定时刷新，替代每请求触发**：`_refresh_if_needed` 与请求量耦合，高峰期反复触发。建议改为**后台独立线程按固定周期**（如每 10-15 分钟）检查并刷新，请求路径只读缓存、不触发刷新判断。
3. **按 codes 索引，避免全表遍历**：`get_all_snapshot`（L706-724）每次对全部 snapshot/ohlcv 遍历再过滤。建议对 `_snapshot_cache`/`_ohlcv_cache` 建立 `code` 哈希索引（dict 已是 code→data，直接 `dict.get(code)` 即可），选股的 codes 过滤复杂度由 O(N)→O(K)，降低请求耗时。

**验收方式（方舟前端侧）**:
1. 后端快照刷新期间（可触发一次刷新：改某股票最新收盘或删缓存重启），`GET /api/snapshot/ready` 始终返回 200（不再因刷新短暂 503），旧缓存持续可用。
2. 刷新期间选股：不再报「数据服务未就绪 / 等待超过」类错误；刷新完成后自动拿到新数据。
3. `/api/snapshot/all?codes=...` 仅按 codes 少量股票时返回明显加快（不受全市场规模拖累）。

**修复记录（量量，2026-09-18）**:
改动文件：`backend/core/service/snapshot_service.py`（3 点全部落地）+ 新增 `backend/tests/test_snapshot_refresh.py`
1. **双缓存热切换**：`_refresh_if_needed` 触发刷新时**不再置 `_ready=False`**，刷新期间 `_ready` 保持 True、旧缓存继续服务；`_reload_async` 新数据就绪后原子替换 `_ohlcv_cache/_snapshot_cache`（原双缓存机制不变）。
